## 四、外部实现 与 本地 的对照（总览）

| 方面 | 外部实现 | 本地（移植并修复后） |
|---|---|---|
| 代码在哪 | 另一个并行分支 | 本地主干，与其它模块统一维护 |
| 是否实际跑过 | 否，只写完 | 是，端到端跑通并完成入库 |
| 功能范围 | 骨架齐全 | 功能不减少；修正错误、按本地约定适配、补齐需求缺口 |
| 自定义模块里再嵌套自定义模块 | 父模块会把子模块内部的层也重复生成一遍（参数量翻倍），并且会因为算出多个候选输出而直接报错 → 任何真实模型都跑不通 | 每个模块只负责自己的直接子层，嵌套可正常生成 |
| 数值比对 | 两个模型各自随机初始化后直接比对，结果永远不相等 → 验证必然失败 | 比对前把原模型的权重按位置复制到再生成的模型上，只检验连接关系与计算顺序是否忠实 |
| 标准化入库 | 临时目录改名到正式目录时，上一级目录没有先创建 → 必然失败，并且在数据库里留下半截记录 | 先创建上级目录；失败时回滚数据库记录与半成品项目 |
| 验收脚本 | 判断接口返回时只接受对象、不接受列表 → 脚本跑到第 7 步就崩，后面的验收项全不执行 | 修好，可全自动跑完全部验收项 |
| 数值比对脚本 | 判断「某个子模块是否带参数」的写法，对多元素张量会直接报错 → 真实模型走不到比对 | 改用正确判断，真实模型可正常比对 |
| 未参与计算的子模块的处理 | 未考虑；真实仓库里「定义了但没用到的层」会导致「输出不唯一」而无法再生成 | 新增判断：完全没有任何连线的子模块只实例化、不参与输出（首次实现有缺陷，本轮已修，见第五节） |

## 五、移植之后本地做的全部改动（按批次）

### 5.1 移植落地 + 第一次评审（发现 5 处一跑就断的问题）

评审时除了读代码，还对关键环节做了实际复现，判定有 4 处会「端到端必然中断」、1 处「验收脚本必然崩溃」。这些问题在第四节的对照表里已列出，此处不重复。

### 5.2 逐条对照需求原文（需求对齐核查）

把《功能需求》原文、设计文档、实际代码三者逐句对照，覆盖需求第一到第六部分共 16 小节，共登记 **27 条**缺口 / 已记录偏差 / 待实现项。处理原则：

- 只补**已经交付范围内**的全部缺口（本轮补齐）。
- 有 **2 处**如果改了会**改变需求本身的含义**，先不动、只在文档里登记，等后续决策。
- 属于后续阶段（第五、六部分）的，登记后归到阶段 4 / 5。

本轮补齐的部分（举例）：

- 统一检索索引增加「按任务类型 / 按模型 / 按数据集」三个维度，检索界面相应增加控件。
- 模型查看器的层级树与结构图支持展开 / 折叠；每层的形状显示改为「输入 → 输出」。
- 画布启动时拉取后端已入库的模块库（与本地已有模块合并展示，不覆盖本地）。
- 论文检索增加「作者 / 时间范围」过滤、批量下载、PubMed 的摘要与开放获取全文、Kaggle 在缺少凭证时的明确报错。
- 最小可运行命令的候选来源更完整；数据集预处理器增加 FASTA / PDB 的基本读取、图片统一为 RGB 并可选择缩放。

**登记了但本轮不改的 2 处**：

1. **没有代码仓库 / 没有环境的论文，给不出可信度结论**（复现需要指向一个已经就绪的项目环境）。
2. **跨数据集时的输入对齐，目前没有真正作用到评估环节**（字段与列名一致靠两侧过同一套预处理来保证，标签归并尚未生效）。

### 5.3 缺陷清扫（两轮，共 26 条，全部修复）

以「找真实缺陷」为目标，分四路扫描（后端基础服务 / 论文与数据集服务 / 模块四与验收脚本 / 前端），另加接口边界探针。典型问题：

- **安全类**：论文下载、AI 任务、压缩包解压三处的路径穿越（可在数据目录之外建目录或写文件）；接口可传入任意参数绕过权限限制；模型加载可越出项目目录。
- **正确性**：可信度分档把非数值 / 0 的报告值误判为「不一致」，且不做单位换算（0.915 与 91.5% 被误判为不同）；删论文或重新抽取后留下孤儿记录；检索过滤器里的下划线未转义；等等。
- **前端**：结构图的连线完全不渲染（用户截图里「没有连线」就是这个原因）；外部画布一挂载就把形状字段清空（保存时丢字段）；操作按钮可以重复入队。
- **接口语义**：未知 id 的接口返回码不统一，改为 404。
- **验收加强**：验收脚本增加「布局自检」（每个父容器必须包住它全部的后代），历史上「所有节点叠在一起」那类回归会被直接拦下。

### 5.4 画布渲染三类问题

- **节点相互重叠**：根因是布局按固定高度预留，而节点的实际高度随「标题 + 形状 + 参数」变化 → 改为按内容预留高度。
- **子节点被父容器遮挡**：画布上子节点和父容器是平铺渲染的，父容器是不透明实底 → 按层级设置叠放次序，保证子节点永远在父容器之上。
- **信息栏遮住工具栏**：信息栏由绝对定位改为纵向排列（信息栏一行、画布占其余高度）。
- 另外增加了「错误边界」（某块界面渲染出错时显示错误信息而不是整片黑屏），以及针对浏览器翻译插件 / 代码编辑器改动页面结构导致的页面崩溃做了防护。

### 5.5 落地复核补正（一批后续修正）

- 形状已经完整时，直接跳过形状追踪，省掉一次「跑一遍模型」。
- 重复入库时，界面提示「同结构的模块此前已经入库过哪些版本」。
- 最小可运行命令：为**没有入口脚本的库型项目**（例如 GEARS）补「导入顶层包」这种等价的最小验证；拒绝「只有解释器、没有脚本」的候选；把「python 某脚本.py」里的 python 换成项目环境的解释器（而不是在前面再加一个解释器、导致找不到文件）。
- 重建项目环境之前先清空旧目录（否则新旧依赖混装，导入就失败）。
- 安装依赖失败时，AI 给出的「修正建议」自身失败不再中断整个流程，改为如实记录并继续，把依赖安装的真实报错暴露出来。
- 安装命令统一加上重试与读超时（本机网络下载大包容易超时）。
- 给项目子进程注入一个**较短的编译缓存路径**（本机 Windows 未开启长路径支持，编译产物路径过长会写入失败）。

### 5.6 论文库二次验证闭环 + 修两处再生成缺陷（本轮）

用一篇真实论文配套的代码仓库 **GEARS** 走一遍「解析 → 验证」链路，作为「换一个真实项目还能不能用」的验证。

- 它的 MLP 模型的**层尺寸与输入维度由运行期配置决定**，AI 读代码时给不出具体数字，结构描述里的层参数与输入形状都是空的。为此新增了**「把补上的参数写回模型描述」的接口**，人工 / 工具补上具体数值后，整条链路走通并成功入库。
- 复跑时又发现并修复了**代码再生成的两处缺陷**：
  1. 判断「没有被用到的子模块」的函数写在了使用它的位置**之后**，导致任何含自定义模块的模型在再生成时直接报错。
  2. 该判断把「只有一条来自父模块的输入连线」的**输入子模块**也误判为「没被用到」，导致算出两个输出而报错。

### 5.7 让「论文库二次验证」能用标准命令复现（本轮）

上面 5.6 那次虽然跑通了，但靠的是**人工调接口补参数**——别人照文档里的命令跑不出来。本轮把它做成一步到位：

- **先说发现的问题**：AI 对这个真实模型（GEARS 的 MLP）的结构描述**每次都不一样**——同一个模型连续三次跑，分别得到 8 个节点/1 条边、3 个节点/0 条边、6 个节点/0 条边；还会把层尺寸写成 `'sizes[0]'` 这种字符串表达式。原因是这个模型的层结构由运行期参数决定，AI 只能猜。对照之下，示例模型（ResNet）的解析很稳定（多次都是 90 节点/66 条边），所以问题只出在这类「结构由运行期决定」的模型上。
- **做了三件事**：
  1. **拆解后自检 + 重试**：拆完立刻试跑一次「再生成」（纯计算、很快），不通过就重试 AI，并把上一次的失败原因**告诉它**（否则同一个问题问两次还是同样的结果）。
  2. **补参自动化**：「补形状」这一步在项目环境里实例化模型时，**顺手把每一层的构造参数读出来**，并在输入形状缺失时按模型首层推导一个可用形状，自动写回模型描述。**维度类参数以实际实例化的模型为准**（原模型和再生成模型必须同维，比对才有意义）。这样就不用再人工调接口了。
  3. 验收脚本里两处过严的判定放宽（一处要求「定义了但没被调用的层」也有形状；一处要求生成代码超过 500 字符，小模型 499 就被判失败）。
- **结果**：`python scripts/m3_acceptance.py --mode full --light --entry MLP --source <GEARS 仓库路径>` 直接跑通 **5/5**；同时在当前代码上**重跑整套验收 16/16 通过**。
- **顺带发现一个已知问题（未修）**：模块的唯一编号（`module_id`）是把「各层参数」算进签名得到的，而 AI 是否写出某个**可选参数**（例如激活层的 `inplace`）并不稳定 → 同一个模型可能算出不同的编号。示例模型这轮就因为 AI 漏写了 8 处 `inplace` 而得到一个新编号。详见《阶段3实施方案》十一.6 待办。

## 七、环境与运行方式（接手的新 AI 请先读这一节）

- **Python 解释器**：`D:\python.exe`（Python 3.13）。后端依赖装在这个解释器里，**不在**项目内的虚拟环境里，也不在 conda 环境里。
- **启动后端**：在 `backend` 目录下执行 `D:\python.exe -m uvicorn app.main:app --port 8000`。**改完后端代码必须重启**（没有开自动重载），否则界面上的操作仍由旧代码执行——表现为「改了没生效」。
- **依赖下载**：启动后端时建议带上 `PIP_INDEX_URL=https://mirrors.cloud.tencent.com/pypi/simple`（本机直连官方源下载大包容易超时）。
- **AI 终点**：走 DeepSeek 的 Anthropic 兼容接口，已经登录。注意它**不支持「结构化输出」字段**，所以任务结果一律让 AI 写成 JSON 文件、再由后端读取。
- **容器**：Docker 已安装，但只是**可选**能力，默认执行走项目自带的 conda / 虚拟环境子进程；后端用到的 Docker 的 Python 库没装，容器通道要用需要先补依赖。
- **常用命令**：
  - 后端测试：`D:\python.exe scripts/run_tests.py`
  - 前端构建：在 `frontend` 目录 `npm run build`
  - 模块四验收：`D:\python.exe scripts/m3_acceptance.py --mode all --source examples/m3_sample_repo`
  - 论文库二次验证：`D:\python.exe scripts/m3_acceptance.py --mode full --light --entry MLP --source <GEARS 仓库路径>`
- **容易踩的坑**：
  - 改完后端代码忘记重启（见上）。
  - 带反斜杠的 Windows 路径若经 bash 传入，反斜杠会被吞掉，产生奇怪的目录名（曾误建在仓库根）。
  - 本机 Windows 未开启长路径支持，深目录下的编译缓存会因路径过长而失败（已用短路径规避）。
  - 用 Python 3.13 建的虚拟环境装不了「钉住旧版本 numpy」的项目，需要指定兼容的解释器。
  - 推送（push）在本机命令里不可用，需要由人用 GitHub Desktop 手动推送。
