## 六、各任务详细方案

### 1.1 任务管理 + 后台任务队列（依据《模块详细设计》2.1、D2）

- **状态机**：`queued → running → success/failed`；`running → cancelled`；`failed → retry → queued`。
- **接口**：`POST /api/tasks`、`GET /api/tasks/{id}`、`POST /api/tasks/{id}/cancel`、`POST /api/tasks/{id}/retry`。
- **职责边界（关键）**：任务表只存调度状态；结果/报错归 `run_record`（《知识库与数据设计》五.2），不重复落库。
- **实现要点**：后台队列用 asyncio + 内存队列（一期串行，架构八.1「一期采用串行任务队列」），任务状态落库供前端轮询（N5 长任务异步化）。
- **落位**：`backend/app/services/task_manager.py` + `backend/app/api/tasks.py`，表 `task`（建表入 `schema.sql`）。

### 1.2 项目管理与工作区（依据《模块详细设计》2.2、D12）

- **两类项目**，本阶段只实现 `original`（`structured` 归阶段3/4）：`project_type`、`source`（paper/repo/local）、`parent_project_id`、`status`（《知识库与数据设计》八.1）。
- **原始项目目录**：`projects/{id}/` 含 `source/ env/ data/ reports/ runs/`（《知识库与数据设计》二.3）。
- **接口**：`POST /api/projects`（含 type）、`GET /api/projects/{id}`、`GET /api/projects`（按类型筛选）。
- **状态机**：`loading → env_ready → analyzed`（2.2），随模块一进展流转。
- **类型权限**：分析/复现/拆解 API 仅接受 `original`，画布/版本 API 仅接受 `structured`，不符即 400（本阶段校验 original 侧）。
- **落位**：`backend/app/services/project_manager.py` + `backend/app/api/projects.py`。

### 1.3 环境管理：决策树 + 依赖修正循环（依据《模块详细设计》2.3）

- **决策树**：项目自带 `Dockerfile` → 容器（复用基底 `runner.py` docker 模式）；否则按 README/依赖清单选 conda 或 venv。
- **版本判断**：解析依赖清单 + 代码 `import` → 语言/框架/CUDA 版本（需求一.2）。
- **修正循环**（核心算法，2.3）：
  1. 按清单安装（固定代码）；
  2. 失败 → 解析报错定位失败包；
  3. agent 判断代码实际用到的库（import 扫描 + 代码阅读）→ 降级/替换版本、移除未实际使用项；
  4. 重试，上限 3 次；
  5. 仍失败 → 项目标记「环境不可用」，原因写入运行记录。
- **接口**：`POST /api/projects/{id}/env`、`GET /api/projects/{id}/env`。
- **每次安装尝试 → `run_record(run_type=env_install)`**，报错入 `error` 字段（供阶段5 蒸馏依赖冲突结论，需求六.1）。
- **落位**：`backend/app/services/env_manager.py` + `backend/app/api/environments.py`；agent 判断 prompt 入 `agents/prompts/dependency_fix.md`（O4）。

### 1.4 检索与下载 + 地址抽取 agent（依据《模块详细设计》2.4）

- **论文检索**（固定代码）：arXiv API / PubMed E-utilities / bioRxiv API，返回列表 → 用户勾选 → 批量下载。
- **地址抽取**（agent 任务）：从论文正文/补充材料抽 GitHub/GitLab 仓库地址、Zenodo/Figshare/Kaggle 数据集地址；下载前用 `git ls-remote`/HTTP HEAD 验证可达。
- **接口**：`GET /api/search/papers`、`POST /api/search/papers/download`、`POST /api/search/extract`。
- **数据集登记** → `dataset_registry`（《知识库与数据设计》八.2）。
- **落位**：`backend/app/services/download_service.py` + `backend/app/api/search.py`；抽取 prompt 入 `agents/prompts/address_extract.md`（O4）。

### 1.5 agent 调度：Claude Agent SDK 集成（依据《模块详细设计》2.5、D3、O2）

阶段1 技术风险最高点，严格按 2.5 实现：

- **任务式定义**：每个 agent 任务 = 一次 Claude Code 会话，构造 `ClaudeAgentOptions`：
  - `cwd`=工作目录（项目工作区）、`add_dirs`、`allowed_tools`、`permission_mode=dontAsk/acceptEdits`、`output_format=JSON Schema(draft-07)`、`max_turns`、`mcp_servers`=知识库 MCP。
- **串行队列**（一期，架构八.1）；每会话专属 `asyncio.Task` 持有 SDK client，经 `asyncio.Queue` 与 HTTP handler 桥接，或每请求 `query()`（官方 issue #576 workaround）。
- **工具白名单（deny 优先）**：读文件（限工作区）、写文件（限工作区）、执行命令（经 `conda run`/`docker exec` 限独立环境）、查询知识库（MCP）。白名单外不提供。
- **模型端点 O2**：默认直连 Anthropic；可选 `ANTHROPIC_BASE_URL` 接 DeepSeek（模型别名重映射），启用前以 MCP 工具调用冒烟测试验收（agent 经 MCP 查知识库一次，验证 tool use 闭环）。
- **异常兜底**（2.5）：`asyncio.wait_for` 整体超时终止会话子进程；429 指数退避；结构化输出重试耗尽→failed 落库；模型忽略/拒绝工具调用→failed，提示换端点；知识带入/冲突预警走后端直查 API 兜底（不受工具调用失败影响）。
- **接口**：`POST /api/agents/tasks`、`GET /api/agents/tasks/{id}`；任务输入输出+日志落盘（N3 可追溯）。
- **落位**：`backend/app/services/agent_service.py` + `backend/app/api/agents.py`。

### 1.6 知识库读写：SQLite + 统一索引 + MCP（依据《模块详细设计》2.6、D9、数据设计二/三）

- **存储**：`data/index.db`（SQLite + FTS5）+ 文件系统并置大文件（D9）。
- **表**：本阶段落地 `unified_index`、`paper`、`run_record`、`task`、`dataset_registry`（`knowledge`、`module` 表可先建空表，schema 见数据设计四~八）。
- **统一索引**：`unified_index` 跨类型（paper/run/knowledge/module/dataset），字段按数据设计三.1；FTS5 虚表 `unified_index_fts` 对 title/summary/keywords/tags 建索引。
- **入库原则**：入库与索引同步写（「先落库后检索」，数据设计一.2），事务内完成。
- **stdio MCP server**：暴露知识库查询能力，供 agent 会话每会话临时挂载（2.6）。
- **接口**（数据设计十清单，本阶段实现前 4 个 + bring 预留）：`POST /api/knowledge/ingest`、`GET /api/knowledge/search`、`GET /api/knowledge/items/{data_type}/{id}`、`GET /api/knowledge/list`。
- **落位**：`backend/app/db/schema.sql`、`backend/app/services/knowledge_service.py`、`backend/app/mcp/knowledge_mcp.py`、`backend/app/api/knowledge.py`。

### 1.7 模块一全流程（依据《模块详细设计》3.1~3.7，收口主线）

串起 1.2~1.6，实现需求一：

| 子项 | 依据 | 要点 |
|---|---|---|
| 3.1 论文检索下载 | 复用 1.4 | 创建 `paper(status=downloaded)`，写 `unified_index` |
| 3.2 仓库与数据集抽取 | 复用 1.4 | 抽地址 → 验证 → 克隆到 `source/`、登记数据集 |
| 3.3 任意项目加载 | `POST /api/projects` | 仓库地址/本地路径 → 建 `original` 项目，本地路径挂载不拷贝 |
| 3.4 独立环境 | 复用 1.3 | 无额外流程 |
| 3.5 最小命令验证 | `POST /api/projects/{id}/verify` | 候选命令优先级 README → 脚本目录 → `--help`；跑通判定随项目类型；全失败 → agent 构造命令 |
| 3.6 静态结构扫描 | `scripts/scan_structure.py` + `POST .../analyze`、`GET .../report` | 产出 `structure_report.json`，schema：`{entry_points[], model_files[], train_flow, inference_flow, module_hierarchy(树), dependencies[{name, version_spec, used_in}]}`；不确定点标 `uncertain` |
| 3.7 动态补充 | agent 任务 | 仅当报告有 `uncertain` 项触发；agent 只读不改，每条记录代码位置+理由 |

- **固定脚本**：`scripts/scan_structure.py`（T4 固定脚本约定，Python 解析 import + AST 识别 `nn.Module` 子类）。
- **落位**：`backend/app/api/analysis.py`（verify/analyze/report）+ `scripts/scan_structure.py` + `agents/prompts/dynamic_analysis.md`。

## 七、端到端主链路（M1 验收路径）

```
POST /api/projects (仓库地址/本地路径)
  → 建 original 项目 + 工作区目录
  → POST /{id}/env (决策树建环境 → 修正循环 → env_ready)
  → POST /{id}/verify (最小命令跑通 → run_record[smoke_run])
  → POST /{id}/analyze (scan_structure.py → 静态报告)
  → [有 uncertain] agent 动态补充 → 合并报告
  → GET /{id}/report (JSON 可入库)
全程 run_record 自动落库
```

## 八、M1 验收落地方式

| 验收项（开发计划·五） | 怎么测 |
|---|---|
| 任意 GitHub 仓库 → 克隆 → 独立环境 → 最小命令跑通 | 选 1 个简单但真实的 PyTorch 仓库走通全链路（conda 例） |
| 依赖修正循环处理一次真实安装失败 | 选 1 个版本不匹配的仓库，验证修正循环收敛（venv 例）；再 1 个带 Dockerfile 的仓库（容器例）——对应「conda/venv/容器各覆盖一例」风险项 |
| 结构分析报告含静态扫描 + agent 动态补充 | 选 1 个含动态构建的仓库，验证 `uncertain` 项被 agent 补充 |
| 运行记录全自动落库 | 全链路结束后查 `run_record` 表，`env_install`/`smoke_run` 等记录完整且 `error` 字段可溯源 |

## 九、风险与应对

- **依赖修正循环 agent 判断质量是最大不确定性** → 用 M1 真实项目反复打磨 `dependency_fix.md` prompt（O4），这是阶段1 最需要迭代的地方。
- **环境类型众多** → 测试按 conda/venv/容器各覆盖一例。
- **agent 端点（O2）** → 先做 MCP 冒烟测试，失败即退回默认 Anthropic 端点，不阻塞其他任务。
- **前置缺失（基底未就位）** → 1.1/1.2/1.6 可先行；1.3 环境管理的容器分支与运行验证需等 `runner.py` 就位后补齐。
