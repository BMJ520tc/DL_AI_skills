## 一、概述与设计原则

### 1. 定位

本文档定义知识库中四类数据(论文数据、模型运行数据、蒸馏知识、标准化模块,对应需求六.1)及支撑数据(数据集登记、项目工作区)的存储选型、目录布局、schema、统一索引与检索接口。本文档是模块二、四、六的接口契约:《模块详细设计》中各模块的入库与检索均引用本文档的 schema 与接口。

术语与决策编号沿用《系统架构设计》一.4 与附录 A/B。

### 2. 设计原则

- **溯源**:每条数据可追溯到其来源——论文数据追溯到 paper,运行数据追溯到 run 与 task,标准化模块追溯到来源项目与验证记录,蒸馏知识追溯其依据的 paper 与 run。
- **结构化与文件并置**:结构化记录入索引库(SQLite),便于检索与过滤;大文件(PDF、markdown、模块代码、运行产物)入文件系统,记录中存路径引用。
- **先落库后检索**:数据产生即入库,检索不直接扫描文件系统;运行数据全自动落库,无需用户操作(需求六.1)。
- **版本化**:所有表带 schema_version 字段,结构演进可迁移(见九.3)。

## 二、存储选型(D9 定案)

### 1. 候选对比

| 方案 | 检索能力 | 事务与一致性 | 部署复杂度 | 需求依据 |
|---|---|---|---|---|
| 纯结构化文件(JSON) | 需自建索引 | 弱 | 低 | — |
| SQLite + FTS5 | 结构化过滤 + 内置全文检索 | 单文件事务 | 低,零服务依赖 | 需求六.1 统一索引 |
| PostgreSQL | 结构化过滤 + 全文检索 | 强,多进程 | 高,需独立服务 | — |
| 向量库 | 语义相似检索 | 弱 | 高,需独立服务 | 需求未要求语义检索 |

### 2. 定案

**SQLite(FTS5 全文检索)+ 文件系统并置大文件**。理由:需求六.1 要求"各有存放结构并统一索引,可按任务类型、模型、数据集检索",SQLite 以单文件满足结构化过滤与全文检索,零运维;PostgreSQL 与向量库引入独立服务,需求无依据,列为过度设计。向量语义检索列为开放项 O1,二期候选,一期仅在统一索引表预留 embedding 字段。

### 3. 数据目录布局

```
data/
├── index.db                     # SQLite 索引库(全部结构化记录 + FTS5)
├── papers/{paper_id}/           # PDF 原文、markdown 全文
├── projects/{project_id}/       # 项目工作区(原始项目 / 结构化项目两类,见八.1)
│   ├── source/                  # 代码仓库克隆
│   ├── env/                     # 独立环境
│   ├── data/                    # 项目自带或下载的数据集
│   ├── reports/                 # 结构分析报告等 JSON
│   └── runs/                    # 运行产物(权重、日志、指标文件)
├── modules/{module_id}/{module_version}/   # 标准化模块包(代码 + module.json + ir.json + assets/)
├── runs/                        # 跨项目运行记录附件归档(可选,默认留工作区)
├── knowledge/                   # 蒸馏知识附件(可选)
└── datasets/                    # 公开数据集本地副本
```

data/ 整体 gitignore(见《系统架构设计》六.3);结构化项目的版本管理不在此目录,而在各自 git 仓库(《系统架构设计》八.4)。

## 三、统一索引与检索

### 1. 统一索引表

跨四类数据及数据集登记的一张索引表 unified_index,支撑"按任务类型、模型、数据集检索"(需求六.1):

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT PK | 索引条目 id |
| data_type | TEXT | paper / run / knowledge / module / dataset |
| ref_id | TEXT | 指向该类型主记录的 id |
| title | TEXT | 条目标题 |
| summary | TEXT | 摘要 |
| source_project_id | TEXT | 来源项目 |
| task_type | TEXT | 任务类型(分类/回归/分割/检测/序列预测等) |
| model_name | TEXT | 关联模型 |
| dataset_name | TEXT | 关联数据集 |
| tags | TEXT(JSON) | 标签数组 |
| keywords | TEXT | 检索关键词 |
| embedding | BLOB 可空 | 向量预留字段(O1,一期不写入) |
| schema_version | TEXT | 索引结构版本 |
| created_at / updated_at | TEXT | 时间戳 |

FTS5 虚表 unified_index_fts 以 title、summary、keywords、tags 建全文索引,与原表保持行对齐;关键词检索即查 FTS,条件过滤查原表。

**id 格式约定**(与实现一致,`knowledge_service.index_entry`):通用条目 `id = "{data_type}:{ref_id}"`;module 因复合主键 `(module_id, module_version)`,其 `ref_id = "{module_id}:{module_version}"`,即 `id = "module:{module_id}:{module_version}"`。

### 2. 检索接口

GET /api/knowledge/search,查询参数:types(可多值,逗号分隔)、task_type、model、dataset、q(关键词,FTS)、limit、offset。返回:命中条目列表(索引字段 + 类型相关摘要字段),按更新时间倒序。一期不做语义检索(O1)。

### 3. 检索结果带入新任务

新任务开始时的知识带入不走通用 search,而走 POST /api/knowledge/bring,按任务类型、模型、数据集组合检索并聚合为建议(参数推荐、依赖冲突预警),与《模块详细设计》八.2 对接。

## 四、论文数据

对应需求六.1 第一项:论文内容(方法、实验设置、结论)及可信度对照结果。来源为模块二全流程。

### 1. 入库时机与来源

- 模块一检索下载论文时创建 paper 记录(status=downloaded)(需求一.1);
- 模块二 PDF 转 markdown 后更新全文与章节索引(status=parsed)(需求二.1);
- 实验条目抽取完成写入 experiment_item(status=extracted)(需求二.2);
- 复现与对照完成写入 reproduction_result 与 credibility_conclusion(需求二.3)。

### 2. 存储形态

papers/{paper_id}/ 存 PDF 原文与 markdown 全文;结构化记录入 index.db,并同步写 unified_index 条目。

### 3. schema

**paper**

| 字段 | 类型 | 说明 |
|---|---|---|
| paper_id | TEXT PK | 优先用 arXiv id 等外部 id,否则内部生成 |
| title / authors / abstract | TEXT / JSON / TEXT | 元信息 |
| source | TEXT | arxiv / pubmed / biorxiv |
| url / published_date / license | TEXT | 出处与许可 |
| pdf_path / markdown_path | TEXT | 文件路径 |
| section_index | TEXT(JSON) | 章节、表格、公式、图注的位置索引(需求二.1 保留项) |
| status | TEXT | downloaded / parsed / extracted / reproduced / concluded |

**experiment_item**(实验条目,需求二.2)

| 字段 | 类型 | 说明 |
|---|---|---|
| item_id | TEXT PK | 条目 id |
| paper_id | TEXT FK | 所属论文 |
| section_ref | TEXT | 来源章节引用 |
| dataset_name | TEXT | 数据集 |
| split_method | TEXT | 划分方式 |
| metric_name / metric_value_reported / metric_unit | TEXT | 评价指标与论文报告值 |
| hyperparams | TEXT(JSON) | 超参数 |
| baselines | TEXT(JSON) | 对比基线及报告值 |
| status | TEXT | extracted(抽取未确认) / confirmed(经确认闸门生效,见《模块详细设计》4.5-3) |

**reproduction_result**(复现对照,需求二.3)

| 字段 | 类型 | 说明 |
|---|---|---|
| result_id | TEXT PK | 对照结果 id |
| item_id | TEXT FK | 对应实验条目 |
| run_id | TEXT FK | 对应运行记录(五章) |
| metric_value_actual | TEXT | 实际数值 |
| deviation | REAL | 与报告值的相对误差 |
| passed_threshold | INTEGER | 是否在阈值内(D6) |
| verdict | TEXT | 一致 / 近似 / 不一致 / 无法复现(D6) |
| evidence_path | TEXT | 佐证产物路径(日志、指标文件) |

**credibility_conclusion**(可信度结论,需求二.3)

| 字段 | 类型 | 说明 |
|---|---|---|
| conclusion_id | TEXT PK | 结论 id |
| paper_id | TEXT FK | 所属论文 |
| overall_verdict | TEXT | 总体可信度分档 |
| summary | TEXT | 结论文本(agent 起草) |
| item_results | TEXT(JSON) | 各条目对照摘要 |
| created_at | TEXT | 时间戳 |
| schema_version | TEXT | 结构版本 |

## 五、模型运行数据

对应需求六.1 第二项:每次实际运行的记录,包括环境配置、参数、运行结果、报错信息。

### 1. 入库时机

环境安装、最小命令验证(模块一),实验复现(模块二),基准与跨数据集评估(模块三),新模型训练(模块五)——全部自动落库,无需用户操作。

### 2. 与任务管理的职责划分

任务记录(task)管调度状态(排队/运行/成功/失败/取消,见《模块详细设计》2.1),运行记录(run_record)管运行结果;一次任务可含多次运行,一次运行对应一条 run_record。避免重复落库:调度进度只写 task,结果与报错只写 run_record。

### 3. 存储形态

结构化记录入 index.db,并写 unified_index;日志全文、权重等大产物留项目工作区 runs/,记录存路径引用;报错信息(文本)入 DB,参与 FTS 检索。

### 4. schema(run_record)

| 字段 | 类型 | 说明 |
|---|---|---|
| run_id | TEXT PK | 运行 id |
| project_id / task_id | TEXT FK | 所属项目与任务 |
| run_type | TEXT | env_install / smoke_run / reproduce / baseline / eval / train |
| environment | TEXT(JSON) | 环境类型(conda/venv/容器)、语言/框架/CUDA 版本、依赖清单 |
| params | TEXT(JSON) | 运行参数与超参 |
| command | TEXT | 执行命令 |
| status | TEXT | success / failed / timeout |
| metrics | TEXT(JSON) | 结果指标 |
| error | TEXT | 报错信息(全文检索) |
| artifact_path / log_path | TEXT | 产物与日志路径 |
| started_at / finished_at / duration_s | TEXT / REAL | 时间与耗时 |

## 六、蒸馏知识

对应需求六.1 第三项:从论文数据与模型运行数据提炼的可复用结论。

### 1. 定义与示例

需求给出的三类示例与类型枚举对应:「某类数据用某组参数效果更好」→ param_advice;「某个依赖在某个版本下会冲突」→ dependency_conflict;「某篇论文的结论在本环境复现不一致」→ reproduction_discrepancy。另含模块三产出的使用建议(usage_guidance)与模块六.2 产出的综合分析结论(fusion_insight)。

### 2. schema(knowledge)

| 字段 | 类型 | 说明 |
|---|---|---|
| knowledge_id | TEXT PK | 知识条目 id |
| type | TEXT | param_advice / dependency_conflict / reproduction_discrepancy / usage_guidance / fusion_insight |
| title | TEXT | 标题 |
| content | TEXT | 自由文本结论 |
| structured | TEXT(JSON) | 类型相关结构化字段(如 param_advice:{task_type, params, dataset_type};dependency_conflict:{pkg, version_a, version_b, resolution}) |
| sources | TEXT(JSON) | 来源引用:[paper_id / run_id / module_id](溯源原则) |
| confidence | TEXT | high / medium / low |
| scope | TEXT(JSON) | 适用范围:任务类型、数据类、模型类 |
| status | TEXT | draft / confirmed / superseded |
| created_at / updated_at | TEXT | 时间戳 |

### 3. 提炼流程与状态机

agent 起草 → draft;用户确认 → confirmed;被后续运行推翻 → superseded(保留记录,检索时默认不返回)。流程细节见《模块详细设计》八.3。

## 七、标准化模块(D10 定案)

对应需求六.1 第四项:模块四拆解并验证通过后入库的标准化模块,附来源项目、任务类型、输入输出规格等元信息。

### 1. 模块包结构

```
modules/{module_id}/{module_version}/
├── module.py          # 再生成的代码:继承 nn.Module 的类(需求四.1)
├── module.json        # 元信息
├── ir.json            # IR 快照(验证与再生成的输入)
└── assets/            # 空目录,预留权重(当前不写入)
```

与实现一致(`decompose_service` 生成模块包):落地为 `module.py`(再生成代码)+ `module.json`(元信息)+ `ir.json`(IR 快照)+ `assets/`(空目录),四者同置于模块包目录。

module.json 字段:

| 字段 | 类型 | 说明 |
|---|---|---|
| module_id / module_version / name / description | TEXT | 标识与描述 |
| source_project_id / source_paper_id | TEXT | 来源项目与论文(溯源) |
| task_type | TEXT | 任务类型(需求四.3) |
| input_spec / output_spec | TEXT(JSON) | 输入输出规格:形状、dtype(需求四.3) |
| params_schema | TEXT(JSON) | 可调参数 schema(需求四.1 用户可调层级参数) |
| tags | TEXT(JSON) | 标签(需求四.3) |
| verification | TEXT(JSON) | 两步验证记录:结构比对与数值比对结果、验证时间(需求四.2) |
| saved_module_compat | TEXT(JSON) | 与基底 SavedModule 结构兼容的字段 |

### 2. 与基底 moduleRegistry 的衔接

基底前端将 SavedModule 持久化在 localStorage(utils/moduleRegistry.ts)。设计改为:模块包由后端持久化并写入统一索引;前端启动或用户触发导入时经 API 拉取模块清单,注入基底 moduleRegistry,保持 ModuleRefNode 与 SavedModule 结构兼容。基底改造点见《模块详细设计》七.1。

### 3. 版本与升级

模块修订 = 新增 module_version 目录,不覆盖旧版本;被引用的旧版本保留(引用关系见九.2),前端默认展示最新版本,历史版本可查看。

## 八、数据集与项目数据(支撑数据)

### 1. 项目工作区目录规范

项目记录字段:project_id、project_type(original / structured)、source(paper / repo / local / decompose / canvas)、parent_project_id(结构化项目溯源其原始项目)、name、status、workspace_path(工作区绝对路径)、created_at / updated_at、schema_version(与实现一致,`project` 表)。

按类型区分两类工作区(D12):

- **原始项目(original)**:projects/{project_id}/ 含 source/(代码)、env/(独立环境)、data/(数据集)、reports/(分析报告)、runs/(运行产物)。仅承载分析与运行,不可在画布上修改。
- **结构化项目(structured)**:projects/{project_id}/ 含 graph.json(网络定义,画布状态)、runs/(运行产物)、exports/(导出代码),工作区根即 git 版本仓库(《模块详细设计》七.6);拆解验证通过时由模块四生成(parent_project_id 溯源),或画布新建。

工作区由《模块详细设计》2.2 的项目管理服务创建与维护;原始项目工作区与模块一的创建独立环境衔接。

### 2. dataset_registry(数据集登记)

支撑模块三的公开数据检索与六.2 的同口径对齐:

| 字段 | 类型 | 说明 |
|---|---|---|
| dataset_id | TEXT PK | 数据集 id |
| name / url / source | TEXT | 名称、出处(zenodo / figshare / kaggle / 自带) |
| task_type | TEXT | 任务类型 |
| format | TEXT | 格式(CSV、Excel、FASTA、PDB、图片、压缩包) |
| fields | TEXT(JSON) | 字段说明 |
| labels | TEXT(JSON) | 标签体系 |
| alignment | TEXT(JSON) | 跨数据集对齐信息:字段映射、序列长度、标签归并(需求三.2) |
| license | TEXT | 许可证 |
| local_path | TEXT | 本地副本路径 |

模块一登记新数据集(需求一.1);模块三每次跨数据集对齐后更新 alignment(需求三.2);模块六.2 以 alignment 保证同口径比较(需求六.2)。

## 九、数据生命周期与一致性

### 1. 数据流向总表

| 数据类型 | 写入方 | 读取方 |
|---|---|---|
| paper / experiment_item / reproduction_result / credibility_conclusion | 模块二(经知识库服务) | 模块六、前端展示 |
| run_record | 基础服务(运行执行时自动) | 模块六、模块三对比分析 |
| knowledge | 模块六(用户确认后) | 模块六(任务带入)、模块一(冲突预警) |
| module(模块包) | 模块四(验证通过后) | 模块五(画布拼接)、模块六(检索) |
| dataset_registry | 模块一(登记)、模块三(对齐更新) | 模块三、模块六.2 |

### 2. 删除与归档

- 被引用的数据禁止删除:模块被网络引用、数据集被项目引用、蒸馏知识被来源引用时,删除请求被拒绝并提示引用关系。
- 过期数据用归档(superseded、status 标记)替代物理删除。

### 3. schema 版本与迁移

- 所有表与 JSON 字段带 schema_version;新增字段采用可空默认值迁移,不破坏旧记录。
- 迁移脚本随 backend/ 代码一起版本管理;index.db 结构变更必须附带迁移脚本。
