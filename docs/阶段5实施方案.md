## 一、文档说明

本文是阶段5（模块六：自迭代与多模型综合分析）的实施草案，按《开发计划》十节的任务
5a～5c 展开：任务分解、实施顺序、验收方式与风险。结构沿用《阶段3实施方案》《阶段4实施方案》。

**本阶段的一个前置事实**（决定了工作量分布）：阶段1～4 已把模块六的**数据底座**基本铺好——
统一索引与三维检索、知识库全部端点、前端只读检索面板、MCP 知识库服务、以及「任务前带入接入模块四」
和「两条硬编码蒸馏路径」均已实现。因此 5a 主要是**收口与补缺**，**5b 是主要工作量**，5c 为从零新增的扩展项。

**缺口（本阶段要做的事）**：

1. **带入触发点只接了 1/N**：设计八.2 要求固定代码触发「模块一加载新项目、模块三新数据集评估、模块五新模型运行」，
   现状仅模块四拆解接入；模块一、模块三、模块五三处未接。
2. **带入产物未落地到操作面**：设计八.2 要求 param_advice「默认填入参数面板或命令模板（用户可改）」，
   现状只把带入结果塞进拆解 agent prompt，界面上看不到、改不到。
3. **依赖冲突未在安装前生效**：设计八.2 要求 dependency_conflict「在安装依赖前提示绕开方案」，
   现状 `env_manager` 只在**失败后**起草冲突知识，安装前**不查询**历史冲突 → M6 第二条验收（安装前生效）不满足。
4. **任务后蒸馏不通用**：设计八.3 要求「任务成功或失败结束 → agent 起草结论 → draft 入库 →
   冲突检测（冲突则 superseded）→ 用户确认 → confirmed」，现状只有两条**硬编码**起草路径，
   无通用 agent 起草、无冲突检测/superseded 代码路径、无确认界面（`confirm` 端点存在但无 UI/无入口）。
5. **多模型综合分析（5c）整体缺失**：无 `POST /api/multi-model/*`、无 `GET /api/multi-model/{id}`。
   注意设计八.4 的**命名冲突提示**：既有 `backend/app/api/analysis.py` 已占用
   `/api/projects/{project_id}/analysis/*`（verify/analyze/report/baseline/compare…），
   多模型分析不得沿用 `/api/analysis/*`。
6. **检索界面细节**：设计八.1 要求「结果按类型分栏展示」；现状为单一平铺列表（带类型徽标）。

## 三、阶段目标

自迭代闭环与多模型综合分析。

- **M6**：
  - 闭环走通：知识入库 → 检索 → 带入新任务 → 运行 → 蒸馏回写；
  - 依赖冲突预警在安装前生效并绕开真实冲突。
- **M7**（扩展）：
  - 两个以上模型同口径综合分析报告产出，结论（fusion_insight）蒸馏入库。

**5b-2（任务后蒸馏）**两半，与阶段4 拆 4d-1/4d-2 同法。

```
5a 检索与入库收口 ──→ 5b-1 任务前带入接入全部触发点 ──→ 5b-2 任务后蒸馏通用化 ──→ M6
                                                                        └──→ 5c 多模型综合分析 ──→ M7
```

| 任务 | 内容 | 依赖 |
|---|---|---|
| 5a | 检索界面按类型分栏；知识库列表/详情收口（复用既有 API，不新建） | 阶段4 |

| 5c | 同口径统一、一致/分歧识别、分歧归因、融合、指标对比、fusion_insight 入库（扩展） | 5b-2（蒸馏入库通道）、阶段2 alignment |

## 六、各任务详细方案

### 5a 四类数据入库与检索收口（依据 8.1、数据设计三）

**实施要点**：

1. **检索界面按类型分栏**：`KnowledgeSearchPanel` 结果区改为按 data_type 分栏
   （paper / run / knowledge / module / dataset），每栏独立计数与折叠；不改动检索/详情逻辑。
2. **知识库 API 完备性核对**：对照《知识库与数据设计》十清单逐端点核对——
   ingest / search / items / list / delete / confirm / bring 均已存在；本任务**只补缺、不新建重复端点**。
   核对 `ingest` 的 data_type 分发是否覆盖 module（现状 `record_module` 存在，`ingest` 路由未列入——
   需核实并按需补齐，属「文档清单 vs 路由」对齐）。
3. **入口与守卫**：确认检索面板入口（`FlowEditor` 知识库按钮）在原始项目页与画布页均可达；
   只读面板不改画布状态（既有约束回归）。

**验收判据**：按类型分栏展示正确、各栏计数与筛选一致；API 清单逐条可达；详情接口对标量/JSON 字段渲染正确。

### 5b-1 任务前知识带入接入全部触发点（依据 8.2、数据设计三.3）

**实施要点**：

1. **接入三个缺失的固定触发点**（设计八.2 原文：模块一加载新项目、模块三新数据集评估、模块五新模型运行）：
   - 模块一加载项目（`analysis_service` 加载/分析链路）→ `bring_knowledge(task_type=?, model=entry_cls)`，
     建议项附在结构分析/环境创建前的提示位；
   - 模块三新数据集评估（`compare_service`/`baseline_service` 评估链路）→ `bring_knowledge(dataset=..., task_type=...)`，
     param_advice 建议进运行/评估参数；
   - 模块五新模型运行（`network_service` 训练运行链路）→ `bring_knowledge(model=<结构化项目名>, dataset=...)`。
   统一沿用「**建议而非强制**、无命中静默跳过、带入失败不影响主流程」的既有口径（`decompose_service` 的 try/except 兜底先例）。
2. **param_advice 落地操作面**：设计八.2 要求「默认填入参数面板或命令模板，用户可改」。
   在画布运行面板、原始项目命令模板处，展示带入的 param_advice 作为**可编辑默认值**（可忽略/清空）。
3. **dependency_conflict 安装前预检**：`env_manager` 创建环境/安装依赖**之前**调
   `bring_knowledge(...)` 取 dependency_conflict，命中则把「绕开方案」并入依赖安装策略
   （修正循环优先采用），并在任务进度中可见。**这是 M6 第二条验收的关键**——现状只在失败后起草（缺口 3）。

**验收判据**：三个触发点在各自流程中均产生「带入建议」（有命中/无命中两种行为可验）；
param_advice 在面板中以可编辑默认值出现；**预置一条真实冲突知识后，安装前即被提示并按绕开方案避开**
（M6 第二条）。

### 5b-2 任务后蒸馏入库通用化（依据 8.3、数据设计六.3）

**实施要点**：

1. **统一触发点**：在任务结束路径挂蒸馏起草。设计八.3 原文触发为「任务成功或失败结束」；
   落地建议在 `task_manager._execute` 的 success/failed 收口处统一触发，**按任务类型白名单**决定是否起草
   （见待裁决项 K2），避免对所有任务（含纯查询类）跑 agent 起草。
2. **agent 起草**：新增 agent 任务（经 `agent_service`，2.5 口径；结果经 result.json 回读），
   依据本次 `run_record` 与相关历史知识产出蒸馏结论（type 限定在五类枚举内），空结论**不产生条目**（八.3 异常边界）。
3. **冲突检测与 superseded**：draft 入库前，按「type + scope + structured 关键字段」与已 confirmed 知识比对，
   冲突时路径为 draft 落库 + 标冲突 + 提供 supersede 操作（数据设计六.3 状态机 draft→confirmed→superseded）。
   **现状 `superseded` 无代码路径，需新增**。
4. **确认流程与界面**：`POST /api/knowledge/confirm/{id}` 已有；补前端 drafts 列表 + 确认/否决（supersede）界面，
   入口可挂在检索面板内或独立管理页（范围待评审判定，见 K4）。
5. **保留两条既有硬编码路径**：`compare_service` 的 usage_guidance、`env_manager` 的 dependency_conflict
   与新的通用通道并存，不回归。

**验收判据**：一次真实运行结束 → 产生 draft（若可提炼）→ 冲突检测可见 → 确认后 confirmed、被推翻者 superseded；
空结论不落条目；检索默认不返回 superseded。

### 5c 多模型综合分析（扩展）（依据 8.4）

**实施要点**（严格按八.4 六步）：

1. **路由与命名**：新增 `backend/app/api/multi_model.py`，前缀 `/api/multi-model`（避开 `analysis.py` 的
   `/api/projects/{project_id}/analysis/*`）。端点：`POST /api/multi-model`（发起分析）、`GET /api/multi-model/{id}`（取报告）。
2. **同口径统一（固定代码）**：以 `dataset_registry.alignment` 统一输出格式、标签体系、评价指标
   （数据设计八.2）；标签体系无法统一时，**不可比部分置为不可比、可比部分继续**（八.4 异常边界）。
3. **一致/分歧样本识别（固定代码）**：按逐样本 `predictions`（`id` 对齐）比对 y_pred；
   需先确认不同 run 的样本 `id` 可对齐（同数据集同 split）。
4. **分歧归因（agent）**：差异来自模型结构、训练数据还是输入适配——agent 起草归因。
5. **融合（固定代码）**：投票 / 加权平均 / 取交集，按任务类型可选（见 K5）。
6. **融合前后指标对比（固定代码）**：复用模块三指标归一（CANONICAL_METRICS）。
7. **结论入库**：把「适用场景 / 分歧原因 / 融合策略效果」作为 `fusion_insight` 蒸馏知识入库（数据设计六.1）。

**验收判据**（M7）：两个以上模型（同一数据集/对齐口径）跑出同口径综合分析报告，
含一致/分歧样本、分歧归因、融合前后指标对比；结论以 fusion_insight 落库可检索。

## 七、端到端主链路（M6/M7 验收路径）

```
M6 自迭代闭环：
  任务运行（真实模块训练 / 环境创建）→ run_record 落库
    → 任务结束 agent 起草蒸馏 → draft（可含冲突）→ 用户确认 → confirmed
      → GET /api/knowledge/search 检索到该知识
        → 新任务（模块一/三/五任一处）bring 命中该知识 → 带入建议（参数/冲突）
          → 按带入建议运行（含安装前冲突绕开）→ 新的 run_record → 回写（闭环）

M7 多模型综合分析：
  同一数据集上 ≥2 个模型评估（各自 predictions 契约 + alignment 已确认）
    → POST /api/multi-model → 同口径统一 → 一致/分歧样本 → 分歧归因
      → 融合 → 融合前后指标 → GET /api/multi-model/{id} 报告 + fusion_insight 入库
```

## 八、M6/M7 验收落地方式

1. **脚本化验收**（沿用 `m4_acceptance.py` 模式）：新增 `scripts/m6_acceptance.py` 与 `scripts/m7_acceptance.py`。

   - M7 逐条断言：两模型 predictions 对齐 → 报告结构（一致/分歧/归因/融合前后指标）→ fusion_insight 落库。
2. **真实数据 + 真建环境**（严口径，沿用阶段4 口径）：真实入库模块/真实结构化项目 + 真实训练运行；

### 收口补记（续）：通用蒸馏通道的**真缺陷**修复（2026-10-04，实测发现）

在上述补记之后，用真实模型端点**实测**通用蒸馏通道（`distill_service`），发现它**实际产不出任何草稿**——
一个此前只被 mock 单测掩盖的真缺陷：

- **现象**：`agent_service.run_sync` 在 DeepSeek 下走 `result.json` 文件兜底（该端点不支持 `output_format`）。
  实测模型**把蒸馏条目直接写成裸数组 `[{...}]`**，而不是 schema 声明的包装对象 `{"knowledge":[...]}`。
- **根因**：`distill_service` 用 `(structured or {}).get("knowledge")` 解析——非空数组会 `AttributeError`
  （被终态钩子的 `try/except` 兜掉、无日志），空数组会被 `or {}` 吃掉；两种情况都表现为「0 条草稿」。
- **修复**：新增 `_knowledge_items()` 归一解析，兼容**裸数组 / 包装对象 / 单条对象**；`multi_model_service`
  的分歧归因同步加形状容错（`reasons` 裸数组）。
- **实测证据**：以一条「torch 与 numpy 版本冲突」的失败记录跑 `on_task_finished` → 产出 1 条
  `dependency_conflict` 草稿（标题「torch<2.1 与 numpy>=2.0 版本冲突导致安装失败」）；分歧归因探针也返回了
  完整 `{summary, reasons}`。
- **回归**：新增 `test_distill_service.py::test_knowledge_items_accepts_all_shapes` 与
  `::test_on_task_finished_handles_bare_array_output` 两条用例锁形状。
- **教训**：mock 单测「返回了正确形状」掩盖了「真实端点返回的是**另一种**形状」。涉及 agent 结构化输出的解析
  必须对形状漂移容错（与 `env_manager._advice_requirements` 同类教训）。

### 收口补记（三）：论文蒸馏——补齐「论文数据」这一蒸馏来源（需求六.1）

需求六.1 的蒸馏知识应来自**论文数据 + 模型运行数据**两类；8.3 原实现只按「任务结束」从 `run_record` 蒸馏，
**缺「论文数据」来源**。本轮补齐：

- `distill_service.distill_paper / distill_papers / paper_distill 任务`：从一篇论文的**实验条目 +
  复现/可信度结论**提炼 draft。类型限 `usage_guidance / param_advice / reproduction_discrepancy`
  （`fusion_insight` 属多模型综合分析专用，越界回落 `usage_guidance`）；`structured.source_paper_id` 标记来源
  并据此**幂等去重**；无实验条目且无复现/结论的论文**不空跑** agent。
- 端点 `POST /api/knowledge/distill`（body `{paper_ids?}`，缺省=全部论文，经任务队列）；
  回填脚本 `scripts/distill_local_papers.py`（默认跳过测试样例论文，`--all` 覆盖）。
- 顺带修复两处**同类的形状漂移**（在真实端点上暴露）：模型把条目包在**以类型名做键**的对象里
  （`{"usage_guidance": [...]}`，甚至带 `paper_id` 兄弟键）、且条目 `type` 漂成 `applicability`/`method`——
  `_knowledge_items` 解析补「任意条目数组值」、新增 `_normalize_type` 类型别名归一。
- **实测（本地真实库 8 篇真实论文）**：产出 **38 条** draft（`usage_guidance` 30 / `param_advice` 10 /
  `reproduction_discrepancy` 1——正对 GEARS 论文「本环境复现不一致」）；`esm3` 无实验条目故 0 条；
  **0 条误标 `fusion_insight`**。草稿在「知识库 → 草稿」页签人工确认。

### 收口补记（四）：自迭代闭环的加固（审核后按「可改的限定」修复）

对《系统架构设计》图 7-4「自迭代回流闭环」逐环节审核，闭环各环节均在且接线正确；
审核发现**一处未经自动验证的接线**并修掉若干可改限定（设计明文规定的不动，见下）：

- **终态钩子接线此前零覆盖**（真缺口）：`task_manager` 是否真的调用注册的终态钩子，
  此前只被「直接调起草函数」的探针绕过。补确定性用例 `test_finish_hooks_invoked_by_task_manager`

  并修掉夹具漏洞——`conftest._reset_task_manager` **漏清 `_finish_hooks`**（进程级全局态会跨用例累积）。
- **草稿必达（原 fire-and-forget 会丢）**：钩子改为**只入队**——白名单任务结束 → 入队 `knowledge_distill`
  任务（持久化、可重试、有进度），起草逻辑移入该任务 handler；崩溃丢的只剩「入队」这一步的极小窗口，

- **论文蒸馏自动化**：论文结论任务（`conclusion`）结束 → 自动入队该论文的 `paper_distill`

- **scope 质量（降噪）**：两条蒸馏 prompt 明确要求「能推断出 task_type/model/dataset 就务必写入 scope」，
  从源头减少「空 scope 命中所有查询」的噪音。
- **设计规定、不改**：八.3「用户确认」（草稿须人工确认才回灌）与 8.2「带入为建议而非强制」是明文设计，
  不属于缺陷，故保持；模块一触发点落在 `analyze` 任务（查看器横幅已覆盖「加载后即可见」）。

### 收口补记（五）：蒸馏结果审核发现的**两处数据质量缺陷**（2026-10-04）

对本地 38 条论文蒸馏草稿逐条审核，**内容质量好**（具体到数值、数据集、种子数、适用范围与注意事项，
GEARS 的 `reproduction_discrepancy` 判断正确）；但发现两处**数据质量/匹配缺陷**并修复：

1. **scope 取值不规范 → 蒸馏知识反而带不出来**：模型给的 scope 出现别名键（`task`）、无关键
   （`conditioning`/`n_measurements`）、**列表值**（`["BioSNAP","BindingDB"]`）与描述句
   （`跨数据集通用（Norman…）`）；而 `_match_scope` 是**字符串严格相等**——只要该维度被查询就把整条**排除**。
   修：① `record_knowledge` 入库时经 `_normalize_scope` 归一（别名 `task→task_type`、剔除无关键）；
   ② `_match_scope` 放宽为**列表任一命中 + 互为子串 + 大小写不敏感 + 别名键容错**。
2. **confidence 超出枚举**：实测出现 `medium-high`（数据设计六.2 只允许 high/medium/low）→
   新增 `_normalize_confidence`（显式别名 + 词根兜底 + 缺失归 low）。

已回填真实库既有行（scope 归一 + confidence 归一，共 10 行；回填后非枚举 confidence 与
非规范 scope 键均为 0）。复验后端 **全绿**。

### 收口补记（六）：链路盘点——补齐两处「无真实案例」的缺口（2026-10-04）

按用户要求盘点全部链路「是否打通 + 是否有真实案例」。结论：**代码全部打通**；真实库中各链路真实案例覆盖

  数值输入；且该项目环境未装 torch）。用**真实仓库文件**（`INGFNN/ESPF/subword_units_map_chembl_freq_1500.csv`

  真实项目环境训练 → **`run_record` train success（accuracy 0.667）** + **运行即提交**（版本树 2 版本）。

### 收口补记（七）：自迭代的「真实提升模型能力」闭环（A + B，2026-10-04；B 属**扩范围**，用户已确认）

回应「自迭代有没有**真实提升模型能力**的案例」——此前**没有**：知识只是「建议」（8.2）、且没有自动化闭环。
本轮 A、B 两项都做：

- **B 自动调参闭环（扩范围）**：新增任务 `network_autotune` + `POST /api/networks/{id}/autotune`——
  带入知识 → 生成候选超参（显式 > 建议 > 围绕 base 的 lr 网格，去重+上限）→ 逐个训练 → 按主指标
  （有 accuracy 取 accuracy、否则 loss）选优 → 记录 `run_record(run_type=autotune)` →
  **把最优超参蒸馏为 `param_advice`（闭环回写，供后续带入）** → 提交带最优指标的版本节点。
  **诚实边界**：只搜**超参**不搜结构；训练脚本不落权重，故「保留最优」体现为记录最优超参 + 蒸馏 + 版本节点，
  不是保存一份更好的权重文件。
- **A 可复现的「提升」演示**：真实数据（数据集的 `frequency` 列取自真实仓库文件
  `ESPF/subword_units_map_chembl_freq_1500.csv`，标签按该列中位数做平衡二分）上——
  差参数（`epochs=1, lr=0.001`）**accuracy 0.494** → 自动调参三候选 `0.78 / 1.0 / 0.98` 选优（`lr=0.01`）→
  最优超参蒸馏为 `param_advice` 草稿 → **确认** → `POST /api/knowledge/bring` 命中该建议 →
  按建议重跑 **accuracy 1.0**。**这是本项目第一个「自迭代真实提升模型能力」的案例**。
- 验证：后端 **359/359**（新增 3 条：候选生成去重/上限、选优 + 蒸馏回写、端点校验）。
